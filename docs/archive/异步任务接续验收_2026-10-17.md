# 异步任务接续验收

> 基准：2026-10-17；`feat/async-task-continuation` 的 HEAD 为 `d7d9588c8d6fb72ce018ad7faf0f74d8f8973923`，审查对象包含全部未提交修改和新增文件。
> 验收对象：`.worktrees/async-task-continuation`；本文为冻结的验收快照。

验收不通过。现有专项测试通过，但真实派发入口、权限边界、终态回执和恢复机制存在阻断，不能认定设计稿的全部功能与验证矩阵已完成。本报告的代码路径和行号均相对被验收工作树，不能拿主树同名文件代替。

## Standards：规范与安全

独立规范审查与主验收交叉核对了以下问题。P1 表示本次交付阻断，P2 表示必须补齐的边界。

### S1 / P1：任务读取和取消没有鉴权

`server/index.ts:223` 直接挂载任务路由，未挂用户认证。`task-continuations.routes.ts:101` 和 `:113` 的查询、取消既不校验用户，也不校验任务凭证和归属。隔离 HTTP 实测：不带任何凭证，知道任务 ID 就能读取完整任务及 `token_hash`，也能取消通知。若部署另外配置了可选 API_KEY，外层可能另有访问限制；任务自己的用户和归属校验仍然缺失。

修复要求：用户接口按用户归属授权，执行器接口按有限权限凭证授权；响应不返回内部凭证摘要。补真实 HTTP 的匿名、错误用户、错误任务和平台模式负例，不能只直接调用服务函数。

### S2 / P2：过期任务凭证仍可提交结果

`task-continuations.service.ts:113` 只比较凭证摘要，不检查 `token_expires_at`。独立审查在隔离库中把有效期设为 `2000-01-01`，完成提交仍成功。

修复要求：按设计定义有效期、终态重复确认窗口和失效规则，并对过期和重复确认分别测试。

### S3 / P1：任务命令继承登记凭证

`cli/task-runner.ts:88` 使用完整 `process.env` 启动任务命令。主验收把登记凭证设为无秘密的测试标记，子命令读取环境后写入 `output.log`，标记确实出现在日志中。任务可获得登记其他任务的能力，违背有限权限边界。

修复要求：为任务命令构造过滤后的环境；执行器自身持有任务回调能力，不把登记凭证、其他任务凭证和用户认证信息传给任务命令。

### S4 / P1：外部结果没有按边界校验

`task-continuations.routes.ts:80` 通过类型断言接受任意非空状态字符串；`task-continuations.service.ts:124` 直接采信客户端 `resultDigest`。`services/task-continuation-recovery.service.ts:61` 把取消、缺失或未知状态默认为 `completed`，`:74` 把文件读取、解析和数据库错误全部静默忽略。

主验收写入 `{taskId, status:'cancelled', exitCode:1}` 的完整结果文件，恢复后数据库为 `completed`、退出码为 1。失败仍写成功的问题没有消除。

修复要求：HTTP 和磁盘输入使用同一套终态与版本校验；服务端计算规范化结果摘要；取消保留为取消，未知状态拒绝或待核对；区分预期的未完成文件与真实读取、数据库错误，并记录可查询原因。

## Spec：设计要求与实际行为

独立规格审查和主验收核对了以下缺失或错误实现。

### R1 / P1：真实 CLI 到宿主的登记与回调没有接通

设计要求任务先绑定原聊天，再后台执行。`server/index.ts:402` 只设置执行器位置和宿主地址；没有生成、绑定、注入原运行的登记凭证。`cli/task-runner.ts:198` 在缺凭证时静默跳过登记，仍显示 `autoNotify: true` 并运行本地命令。独立产品探针请求自动通知，结果为退出码 0、HTTP 请求 0 次，宿主并不知道任务存在。

即使外部补入凭证，真实接口仍有连续错配：

- `register` 没有认证中间件填充 `req.user`，真实 CLI 对路由实测返回 `401 USER_REQUIRED`。
- CLI `:211` 不发送路由 `:45` 必填的 `sessionId`；应从有限权限登记上下文确定归属，不能让模型任填。
- CLI `:221` 读取顶层 `taskId/taskToken/taskDir`，路由返回 `{success,data}`，服务结果也没有 `taskDir`。
- CLI `:248` 在请求头提交 token，正文只提交状态、退出码和 `summary`；路由 `:79` 强制正文 `taskToken/resultDigest`，摘要字段也不同。
- CLI 默认把结果写到工作目录 `.cloudcli/tasks`，恢复默认扫描用户目录 `~/.cloudcli/tasks`，缺少可信的任务目录绑定。

修复要求：统一真实调用契约、凭证上下文、目录管理和结果格式。要求自动通知时登记不可用必须明确失败，不能悄悄执行无通知任务。新增 CLI → HTTP → SQLite 的集成测试，不伪造 HTTP 响应。

### R2 / P1：没有独立后台执行层

设计要求登记后返回任务 ID，任务脱离原 app-server 生命周期。`cli/task-runner.ts:88` 使用 `detached:false`，`:235` 一直等待任务完成，未见独立后台执行器接管。原样使用设计稿命令时，命令工具仍在等待执行结果。执行器仅发一次完成回调，没有重试循环；启动扫描也不能补录宿主已经恢复以后才落下、但回调失败的结果。

修复要求：实现真正的后台执行和持久结果补录，验证父回合结束、父连接关闭后任务存活；回调失败后在宿主持续在线时也能最终补录。仅测试 `spawn` 子命令成功不算后台生命周期验收。

### R3 / P1：引擎失败仍记交付成功

设计明确禁止用 `started` 或 Promise 正常返回判断成功。`server/index.ts:453` 正是 `runRes.started && !runRes.error`，没有取关联引擎回合 ID。主验收让假运行时发送 `complete(exitCode:1)` 后正常返回，真实网关登记为 `engine_failed`，但真实任务派发器仍写 `delivered`，`engine_turn_id` 为空。

修复要求：接收引擎请求时就保存真实关联回合；根据该回合的完成、失败、中断、审批等待更新回执。补“通过完成帧报失败但 Promise 正常返回”的负例。

### R4 / P1：真实过期租约不能按时接管

`task-continuation.repository.ts:293` 写 ISO 时间 `YYYY-MM-DDTHH:mm:ss.sssZ`，`:284`、`:307`、`:344` 与 SQLite `CURRENT_TIMESTAMP` 的 `YYYY-MM-DD HH:mm:ss` 直接作文本比较。同一天内 `T` 大于空格，即使已经过期也不会被视为过期。主验收把租约设为一分钟前的真实 ISO 值，重新领取返回空。

现有测试用 `expireLeaseForTesting` 写 SQLite 格式，人为绕过生产写入格式，不能证明真实租约可接管。修复要求：统一时间表示和比较，使用生产路径与可控时钟测试到期；投递状态更新也必须核对租约拥有者与合法前置状态，不能靠状态机辅助函数的单元测试代替数据库约束。

### R5 / P1：崩溃历史核对未装配，accepted 无恢复

`server/index.ts:431` 没有传 `historyChecker`，所有遗留 `sending` 都只能进入 `needs_review`，不存在已接通的真实 Codex 历史反查。`recovery.service.ts:97` 只查 `sending`，漏掉 `accepted`；实测 `accepted` 恢复后仍原样停住。

即使外部注入检查器，`:127` 把 `found:false` 直接视为未发送并回到 pending；设计明确说“没有查到”不足以证明未发送。找到回合但没有终态时也不能按默认成功写交付。

修复要求：接入真实历史读取和完整分页核对，区分已接收、已成功、已失败、仍运行、证明未发送和无法判断；恢复全部相关状态，结果不确定不重发。使用真正终止并重启的隔离子进程验证，而不是同进程直接调用恢复函数。

### R6 / P1：会话占用竞争会丢失通知

`dispatchTaskContinuationEvent` 先检查空闲，再调用真实网关占用会话。如果用户在检查后先占用，网关返回未启动，派发器把结果写成 `reply_failed`，没有退回 pending。对于同一聊天的多事件，轮询又总领取最老 pending，忙聊天的事件反复退回队首，可能持续阻塞其他聊天。

这两项由源码路径确认，未在主探针中实际竞争复现。修复要求：在运行占用处返回有类型的忙状态并回队列；调度跳过忙聊天，同聊天按序、不同聊天互不阻塞。补可控竞争测试与两个聊天的公平性测试。

### R7 / P1：取消、待确认和停用路径不完整

`task-continuations.service.ts:167` 只有已经生成通知事件才可取消。任务执行中事件尚不存在，因此无法提前取消通知。启动入口无条件启动派发器，没有设计规定的默认关闭开关。`needs_review` 没有认证后的人工确认或显式重投入口。

此外，派发装配把用户固定为 `userId:1`；没有按任务实际用户、归档状态和引擎能力做发送前核对。设计要求不支持的引擎明确拒绝，不能把这些任务当普通空消息运行。

修复要求：落实设计已有的开关、任务级通知意愿、人工处理和目标校验，保持任务取消与通知取消的语义分开。

## 独立产品评审

产品评审结论不通过。真实用户请求 `--notify` 时缺凭证会静默执行本地任务，命令成功但不会自动汇报；任务运行中不能提前取消通知；重启后待确认没有可操作的处理路径；没有统一停用新汇报的开关。独立评审执行了成功短命令与 HTTP 计数，其余产品判断来自源码，没有真实 Codex、浏览器断连和生产重启证据。

不需要产品负责人另做取舍，先实现原设计规定的入口、失败提示、取消与恢复路径。
