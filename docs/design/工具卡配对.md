# 工具卡跨路配对（阶段 4）

> 状态：已勘察，实现待定（需要一份真实 Codex 会话样本才能定方案）
> 目标：弄清"工具卡重复/不配套"的成因，区分可修的与结构性的

## 勘察结论

`toolIdentity.ts` 的匹配顺序是：精确 `toolId` → 完整调用指纹（工具名 + 完整入参）→
Edit 的窄路径。其头注释已经写明两路的 `toolId` 各自推导、可能不同。逐家核对如下。

### claude：两路本来就一致，无需改动

历史与实时都走 `normalizeMessageRows`，`tool_use` 块的 `toolId` 都取 `part.id`
（Anthropic 的 `toolu_…`）。精确匹配可用。

### codex：两个 id 空间无法调和，这是结构性的

| 路径 | toolId | 来源 |
| --- | --- | --- |
| 实时 | `itemId` | SDK `item.id` |
| 历史 | `callId` | rollout 的 `payload.call_id` |

SDK 的 `CommandExecutionItem` 类型**只有 `id`，没有 `call_id`**
（`node_modules/@openai/codex-sdk/dist/index.d.ts`），所以实时侧拿不到 `call_id`；
而历史侧的 `call_id` 是 function_call 与 function_call_output 的配对键，不能改用 `payload.id`，
否则工具结果就配不上自己的调用。

**结论：Codex 工具卡的精确 id 匹配永远不成立，只能走指纹。** 这不是遗漏，是两侧 id 空间不同。
不要再试图用 id 修它。

### codex 指纹也可能对不上（推断，待验证）

已证实的一半：历史侧把一次 exec 脚本里的多条命令**合并成一张卡**，
命令用换行拼接——`codex-sessions.test.ts` 有用例钉住这个行为
（`{ command: 'echo one\necho two' }`）。

未证实的一半：实时侧是否**每条命令各发一个 `command_execution` item**。
若是，则一次双命令脚本会产生「2 张实时卡 + 1 张历史卡」，
`toolId` 与指纹都对不上，三张全渲染——正是"工具卡重复且不配套"的形状。

仓库里没有 `command_execution` 的实时样本或测试，**无法在本地证实**。
需要一份真实 Codex 会话（跑一条含多命令 exec 脚本的回合）来确认实时事件的粒度与
`item.command` 的确切取值。

## 下一步取决于验证结果

- **若实时确实按命令拆分**：两路粒度不同，靠指纹无解，需要在归一化层统一粒度
  （让历史也按命令拆，或让实时按脚本合并），并用适配器层测试钉住"同一次脚本两路产出等价的卡片集"。
- **若实时也按脚本合并**：那指纹应当已经能配上，重复另有来源，需要换方向查。

在拿到样本前不动代码：改错粒度会把"偶尔重复"变成"稳定丢卡"。
