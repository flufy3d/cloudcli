# Codex 会话 "Turn interrupted" 树中断 · 诊断报告

- 状态：已定案（引擎行为；cloudcli 侧缓解方案待实施）
- 基准：v2.7.2 · 引擎 @openai/codex 0.157.1（ec253d31）· 文案修正 cb6bfa59
- 日期：2026-09-28

## 结论

Codex 引擎（V2 多代理模式）在**子代理完成工作的同一秒**，把同一棵代理树里所有其他活跃 turn——父会话的 turn 和兄弟代理的 turn——按 `interrupted` 强制中止。该行为由**引擎 0.154/0.155 线引入**（cloudcli 于 9/18 随 a08e8869 捆绑 0.155.0），与 cloudcli 代码、用户操作、配额、网络全部无关。升级到当前最新 0.157.1 不能解决（上游 0.156/#45549、0.157/#47340 只改"被打断后保留现场"，不取消打断）。cloudcli 侧的"自动续跑"缓解方案待拍板实施。

## 现象

用户在 codex 会话中派发评审类子代理任务后，turn 频繁以 "Turn interrupted" 结束：时间线出现中性中断行（手机 PWA 锁屏时实时错误帧丢失，解锁后只见历史重读的中性行），任务半途而废；重发消息后模型重启代理，代理完成时再次触发中断，形成"越重试越打断"的循环。2026-09-27/28 单会话 7 次中断；全历史扫描确认本周 ≥5 个会话中招。

## 证据链

### 取证面

- 引擎 rollout（`~/.codex/sessions/**/*.jsonl`）：每个 turn 的生灭、工具调用、`turn_aborted` 事件，秒级/毫秒级时间戳。
- 引擎结构化日志（`~/.codex/logs_2.sqlite`）：RPC 记录、进程归属（process_uuid）、client_version。
- cloudcli 服务端日志（`~/.pm2/logs/cloudcli-out-9.log`，无时间戳，按内容锚点定位）。

### 关键证据

1. **同秒配对**：每次父 turn 被打断的同一秒，必有一个子代理 `task_complete`。2026-09-28 复发案例毫秒级时间线：

   ```
   00:23:05.4   代理 a8b0（跨 run 复活的评审代理）发送最后汇报
   00:23:09.492 a8b0 完成（task_complete）
   00:23:09.988 父 turn 被打断（interrupted）      ← 相差 496ms
   00:23:09.989 兄弟代理 c47c 被打断              ← 与父仅差 1ms，同一次横扫
   ```

   该签名在 0.155.0（升级前）与 0.157.1（升级后）上完全一致。

2. **无人发过中断**：cloudcli 端 pm2 日志零条 `chat.abort` / `Aborting session`；引擎日志零条 `turn/interrupt` RPC；app-server 子进程从未自崩（23/23 次退出均为 code 0 且由 cloudcli 正常关闭）。因果方向是引擎先中止 turn、通知 cloudcli，cloudcli 才关连接。

3. **触发姿态**：中招的 turn 全部 spawn 过代理（4/4 vs 未 spawn 的 7/7 全部正常）；代理为**跨 run 复活**（前次 run 结束被陪葬打断，下次 run 引擎 resume 线程时从 rollout 自动复活续跑），其发起 turn 已死，完成时引擎以中断父 turn 的方式强制投递结果，并顺带扫掉兄弟代理。

4. **误导文案**：引擎的 `turn/completed(status=interrupted)` 不携带原因，配额中断与引擎自中断不可区分；旧文案"通常是用量到限"在本场景为误归因（已改中性文案，cb6bfa59）。

## 引入点：全历史扫描（8 月初至 9/28，119 个 rollout）

**横扫签名定义**：被打断时刻 ±5 秒内，同树子代理 rollout 存在 `task_complete`。

| 引擎时代 | 子代理完成且父会话活跃 | 其中被横扫 |
| --- | --- | --- |
| 0.146/0.149 | 1 | 0 |
| 0.153.4 | 81（完成撞父活跃是常态用法） | **0** |
| 0.155+ | 77 | **12** |

时间线：首例 9/21（引擎 0.155.1，originator=codex_sdk_ts 的非 cloudcli 客户端）；cloudcli 首例 9/24；风暴 9/27-28。cloudcli 捆绑 0.155.0 于 9/18（a08e8869）。

**已排除的假设（均有数据）**：

- V2 默认翻转——session_meta 显示 0.146 时代子代理即 `multi_agent_version=v2`；
- 复活机制新引入——0.146.1 时代即有 11 条命的代理，多命贯穿全部时期；
- 用法变化——0.153.4 上"完成撞父活跃"81/83，同场景零横扫；
- cloudcli 代码——窗口内 cloudcli 仅改解析/报告，且外部客户端先中招三天。

**感知层补充**：980d34f1（9/24）之前 cloudcli 把 interrupted 当正常完成处理，实时红错为 9/24 后才有；但 rollout 签名 9/21 前真实不存在，"以前不会"属实。

## 未决问题

- **精确上游 hunk 未钉死**：已逐行 diff 0.153.4→0.155.0 的 agent/control（完全一致）、完成投递函数（一致）、input_queue（元数据管道）、session/handlers、tasks/mod、session/mod、thread_manager（均无关改动）。翻转点在未排查路径，或是概率被时序改变放大的既有竞态。
- **合成复现未打红**：5 轮单连接合成场景（单代理 wait / 双代理错峰 / 长流式中完成 / send_message 唤醒再完成 / 父卡 shell 轮询中完成）全部正常；跨 run 复活是必要触发条件的嫌疑最大，但没有红色复现回路就无法对引擎做二进制定位。

## 已落地

- ec253d31：`@openai/codex` 0.155.0 → 0.157.1。协议面 diff 确认 cloudcli 所用 14 个方法签名未变；72 项 codex 测试、typecheck、lint、build 全绿；新引擎真实 collab 冒烟 + 真实解析器读新 rollout 无漂移。**对横扫无效，但保留现场类修复仍有价值**。
- cb6bfa59：interrupted 错误文案改中性双归因 + "发消息可继续"指引（该指引属实：发消息走 `thread/resume` 续同一会话）。
- 诊断期间产生的探针会话留在 `~/.codex/sessions/2026/09/28/`（originator=repro-probe，首条消息 "You must use the multi-agent…"），可清理。

## 建议

1. **cloudcli 自动续跑（待拍板）**：收到 `status=interrupted` 且非用户停止时，先查配额（复用 quota provider 的 RPC）；配额正常即自动注入一条"继续未完成工作"续跑（上游 daemon_recovery 同思路），时间线加灰字提示，限一次防循环；配额耗尽走原错误路径。
2. **向上游报 issue**：携带本报告的时代对比数据（0.153.4 上 81 次同场景零复现 vs 0.155+ 77 次炸 12 次）与毫秒级签名，要求"复活代理的完成投递应入邮箱而非中断整树"。
3. **不建议回退引擎**：cloudcli 已有适配 0.155 行为的代码（如 033e732b），降级会破坏适配，且 0.155 前版本另有已知问题。
